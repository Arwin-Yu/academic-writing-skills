# rewrite

让读者从正文理解模型在解决什么问题、操作为什么有用、结果怎样。修改技能时不改论文。

## 1. 先找断点

先读所改正文、必要前后段及前文相关定义，不先看段落计划或自评。尝试用日常学术语言复述关键机制及段落联系；说不清就引用原句，指出缺少的前提。必须读取 [执行检查](references/execution-checks.md)，按其中要求留下正文依据。
单段任务只读取理解所需的上下文，在授权范围内修复，不要求每段重复一套问题与答案。

## 2. 补关系，再改句子

按内容需要修复六类关系，不机械套成段落模板：

1. **概念前提：** 优先复用前文概念。新术语未定义时，在首次使用处解释其含义及与已知概念的关系，不只展开缩写。
2. **参数形式：** 说明关键控制量是什么、从何取得、交给谁、控制什么；必要时解释与已有参数的区别或兼容性。形式和维数须有依据，不堆符号。
3. **技术流程：** 按实际依赖说明各模型或模块的职责及输入输出，让上一步的结果接到下一步。相关前提放在使用之前，避免模型之间反复切换。
4. **必要性与收益：** 补足“原有困难及后果 → 必要操作 → 实际改善”，再给已有结果与适用条件。“采用网络”“增加维度”本身不是收益；缩短时删重复和旁支，保留因果。
5. **段落承接：** 说清本段接续前段的哪个问题，或在同一问题上比较什么。用具体操作、结果或限制连接，不用空泛开场补接，也不虚构递进或论文间的改进关系。
6. **具体机制：** 用对象怎样变化解释特征、编码、基和权重等术语，先讲懂关键操作再比较。涉及训练与使用时，区分训练学到什么、使用时输入什么及怎样得到结果。

明确主语、动作和对象，删除空泛开场和重复总结。核实句间真实关系，不只删换连接词；保留必要复句与技术细节，不改成口头问答或机械禁词。
直接陈述具体机制、结果或局限，删去“作者报告了相关限制”“论文对此进行了讨论”等未增加信息的文献转述。前句已说明局限，就不再补报告式收尾；需要区分作者解释、实验观察与本文推断时，保留必要归属。
不改变事实、数字、适用条件、引用或结论强度。缺少机制证据、比较结果、独立论点或跨节冗余，返回 paperwrite；已授权两阶段任务就在原范围内补写，仅润色任务则列出缺口，不自行补造或检索。
总结回答研究问题的解决程度和剩余困难；后句解释前句的原因、条件或结果，不逐篇压缩技术，不拼接检查建议与下节预告。

## 3. 用最终正文复核

按六项检查适用内容，为主要机制及段落联系保存“原句及缺失前提 → 改后原句 → 仅凭正文得到的具体复述”。已有上下文满足的前提标明位置，不重复扩写；不适用的项目说明原因。复述只重复模块名、仍依赖未写出的前提，或段间联系说不清，继续改写。
另查每句是否增加具体信息、论点与结论强度是否保留、是否重复相邻节、总结是否来自前文。核对记录对应最终稿，再处理格式。脚本只验证片段、版本与记录完整性，不能判断六项是否真正满足；同一助手复核如实注明，不冒称独立读者验证。
默认对话交付改稿及必要的内容缺口；文件任务保留初稿、改稿和核查记录。用户只要正文时，检查留在工作记录中。

执行前定位项目已有的写作约定、决策记录、文献库和语言流程；如有 `writing-contract.md`、`review-state.json`、`decisions.md` 或 `BILINGUAL_WORKFLOW.md`，读取与本轮相关的内容。用户最新明确指令优先。未配置这些文件时，使用当前对话和项目实际文件，不强制创建配置文件，也不虚构既有决定。只修改授权范围；文件任务保留初稿、改稿与核查记录，按项目配置验证输出。
